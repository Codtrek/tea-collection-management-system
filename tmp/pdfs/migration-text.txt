Understand schema drift
Schema drift = TypeORM entities and the database schema do not match.
The comparison happens
 after
 pending migration files are executed on the temporary Neon PR database.
The expected schema is described by the
*.entity.ts
files; the actual schema includes columns, types,
constraints, defaults and indexes in PostgreSQL.
Example.
 A developer adds
registration_code
to
estates.entity.ts
but forgets to add the column in a
migration. The entity expects the column, while PostgreSQL does not have it. The workflow's
 Check for
missing migrations
 step fails.
Why it happens

 An entity was changed, but the migration was not created or committed.

 The migration's
 VARCHAR
 length, nullability, default, column name, or type diers from the entity.

 Indexes, foreign-key constraints or check-constraint names do not match.

A PR is being tested against an older Neon Dev snapshot, or changes from another PR introduced a
mismatch.

 SQL changes were made directly in a database without a corresponding migration/entity update.

existing data.

Viewer access versus migration permission
 Neon Console
 Viewer
 permission does not grant
PostgreSQL table modification privileges, and viewers cannot fetch connection strings through the Neon
Console. A separately shared URL, however, authenticates as its embedded PostgreSQL role. If the PR
workflow's
NEON_ROLE
can alter tables, anyone who decrypts that URL may also be able to alter tables
on that temporary PR database
. The shared Dev credential must remain restricted to GitHub Actions
and authorized maintainers. Prefer issuing a separate limited-privilege PR role when developers only
need to inspect schema/data.
Optional read-only diagnostic commands (temporary PR database only):
cd source-code/backend
npx typeorm-ts-node-commonjs migration:show -d src/data-source.ts
npm run migration:generate -- src/migrations/CiDriftCheck --check --dryrun
migration:show
lists applied and pending migrations. The
check dryrun
command inspects schema
dierences without applying them. These diagnostics require a working PostgreSQL connection and
appropriate read access.
 Do not use
npm run migration:run
as a diagnostic
: it executes pending
SQL and usually requires table-owner privileges. Normally the GitHub PR workflow runs the migrations
for you.
Common migration errors and fixes
Migration execution errors occur when PostgreSQL cannot perform a statement in
up()
. Find them under
Checks
!
create-and-migrate
!
Run migrations on the PR branch
. Investigate the
 first failing SQL
statement
, not just the final
 exit code 1
.
1. Permission denied / must be owner of table
ERROR: must be owner of table estate_documents
Cause:
 The connection role can connect but does not own the table or lack appropriate owner-role
privileges for
 ALTER TABLE
.
Fix:
 Ask the database maintainer to check the connected role and the table owner; configure the approved
migration role. Do
 not
 share credentials or try random grants. A normal
GRANT ALL
does not grant table
ownership. This happened in Harboost's shared Dev migration run.
2. Column, table or constraint already exists
ERROR: column ... already exists
 or
 relation ... already exists
Cause:
 Another change already added the object, or the migration history and actual schema dier.
Fix:
 Update from
dev
; inspect the latest migrations and existing schema. Resolve the overlapping change
in the feature branch. Never mark a migration as run merely to silence the error.
3. NOT NULL / unique / foreign-key constraint violation
column ... contains null values
,
duplicate key value
, or
violates foreign key constraint
Cause:
 Existing rows are incompatible with the new rule.
Fix:
 Inspect aected data; use a safe staged change (add nullable column, backfill or clean data, then
apply the constraint), test on an isolated database, and obtain reviewer approval.
4. Missing table, wrong column, or SQL syntax error
relation ... does not exist
,
 column ... does not exist
, or
 syntax error
Cause:
 The migration assumes the wrong schema, order, naming, or SQL.
Fix:
 Compare the SQL with the actual database schema and existing migrations; repair the migration,
push and rerun CI.
5. Migration succeeds, but schema drift fails
Cause:
 SQL was valid but produced a schema dierent from the entity model.
Fix:
 Follow the schema-drift steps above; verify types, defaults, lengths, constraint names and indexes.
6. SSL or dependency warning with successful SQL execution
Cause:
 A driver reports a configuration or deprecation warning, which is not necessarily an SQL failure.
Fix:
 Check the actual step status and first error. Report warnings separately rather than treating them
as migration failures.

If a migration fails on shared Neon Dev:
 stop and inspect the run logs and database state; notify
the maintainer. Transactional operations may roll back, but do not assume every possible migration is
fully reversible. Do not edit the shared database, delete records, alter migration history, or rerun blindly.
Coordinate a corrected migration and a safe retry.

How Harboost's pipeline protects database changes
Safety Gate 1  Before merge (required PR check)
Neon PR branch
runs on PR open and on subsequent pushes (
synchronize
). It creates or reuses
a temporary Neon branch, refreshes it from shared Neon Dev, runs pending migrations, and checks
entity/schema drift. The GitHub
dev
protection rule requires
create-and-migrate
to pass plus the
required reviewer approval and an up-to-date branch.
Safety Gate 2  After merge (shared database update)
Neon Dev Migrations
runs on a push to GitHub
dev
and applies pending migrations to the
 shared
 Neon
Dev database using a GitHub Actions secret. It reports failure if SQL cannot be applied.
 Important:
the merge has already happened when this workflow starts; a failure does not undo that merge and is not
yet wired to block backend deployment.
Human safety check  During review
The reviewer checks that the latest shared Dev migration run for the current
dev
commit has completed
successfully before approving the next migration-related PR. This helps avoid validating work while Dev
is still migrating.
Security controls
Database credentials and the Neon API key are stored in GitHub Secrets; the PR uses an isolated database
branch; the post-merge job uses the shared Dev connection only after merge; role permissions govern
schema changes; and the PR connection string is encrypted before being shown in the Actions summary.
Branch protections reduce accidental merging but cannot guarantee migrations will never fail.
