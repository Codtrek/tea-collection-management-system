# Authentication Architecture Analysis

Repository review date: 2026-11-08
Scope: source-code only; no authentication or schema changes made.

## Executive summary

- Estate Owner authentication is implemented in the mobile app and backend. The mobile login screen calls `POST /auth/mobile/login`; the shared `AuthService.login()` authenticates the `users` row and returns a JWT plus an Estate Owner profile.
- Tea Collector authentication is already implemented on the backend, contrary to what an earlier project-status note might suggest. `POST /auth/agent/login` verifies a Collection Agent login and returns an agent-specific JWT and a `mustChangePassword` flag. The Admin employee-registration path attempts to provision the login and return a one-time temporary password, but there is a likely missing required `users.name` value in the provisioning insert (details below).
- The mobile app is not integrated with this Tea Collector backend flow. The role selector sends "Factory Collector" to a mock screen; its login service calls `/auth/mobile/login`, not `/auth/agent/login`. The mobile API client does not attach bearer tokens, and there is no mobile auth context, protected-route/session-restoration flow, or implemented logout.
- Agent API security is implemented: agent tokens and portal tokens are accepted by separate Passport strategies, and `dispatch/me/*` resolves the current agent from the JWT subject and checks current employee/login status and the temporary-password flag on each call.
- A relevant existing mismatch: `/auth/mobile/me` uses the portal `JwtAuthGuard`, whose strategy accepts only Administrator/Officer/Manager tokens. An Estate Owner or Estate Manager can get a successful login token, but that token is rejected by this guard. This route is not usable by the estate-role mobile session as currently written.
- No new database table appears necessary for Tea Collector login if the current schema and migration are applied. The needed `users`, `factory_employees`, `employees`, and `collection_agents` relationships and temporary-password column are already represented. However, the TypeORM entity and DB baseline require `users.name`, which agent provisioning does not supply, and tracked `init.sql` omits `users.name`/`users.nic`; a fresh-database setup and real provisioning should be verified before depending on the flow.

## 1. Backend authentication architecture

Authentication is implemented with NestJS, Passport JWT, TypeORM, `bcrypt`, and `@nestjs/jwt`. There is no custom `@Roles` or `@CurrentUser` decorator in the authentication path: route protection uses Nest `@UseGuards(...)`, and role/permission checks are performed in strategies or services. `@SkipThrottle` is used on selected login routes.

### Login endpoints and request bodies

| Endpoint | Method | Body / DTO | Purpose |
|---|---|---|---|
| `/auth/login` | POST | `LoginDto`: JSON object with phone and password fields | Shared login entry point, used by the Admin portal service. |
| `/auth/mobile/login` | POST | Same `LoginDto` | Mobile owner/manager login. Calls the same `AuthService.login()` as `/auth/login`. |
| `/auth/mobile/register` | POST | `RegisterDto`: `name`, `phone`, `nic`, `password`, `confirmPassword` | Public Estate Owner registration. |
| `/auth/agent/login` | POST | Same `LoginDto` | Tea Collector login. Calls the separate `AuthService.agentLogin()`. |
| `/auth/agent/change-password` | POST | `ChangePasswordDto`: `currentPassword`, `newPassword` | Agent-only first password change, guarded by `AgentJwtGuard`. |
| `/auth/me` | GET | Authorization header containing JWT | Portal profile; guarded by `JwtAuthGuard`. |
| `/auth/mobile/me` | GET | Authorization header containing JWT | Mobile profile handler; currently also guarded by `JwtAuthGuard`, so it accepts portal roles only (see the role-strategy issue below). |

`LoginDto` checks that `phone` is a string and that password length is at least one; it does not apply the stricter Sri Lankan phone-number format used by registration. `RegisterDto` checks an LK phone number, a valid old/new Sri Lankan NIC pattern, a password of at least eight characters, and matching confirmation. `ChangePasswordDto` checks a nonempty current password and an 8-72 character new password. `main.ts` enables `ValidationPipe({ whitelist: true })`; validation properties not declared in a DTO are stripped.

### Estate Owner login: verified backend sequence

1. The mobile frontend posts `{ phone, password }` to `/auth/mobile/login`.
2. `AuthMobileController.login()` passes both values to `AuthService.login()`.
3. `UsersService.findByPhone()` looks up the unique `users.phone`.
4. `AuthService.login()` returns HTTP 401 (`UnauthorizedException`) if there is no matching user; otherwise it runs `bcrypt.compare(password, user.password_hash)`. A mismatch also returns 401.
5. A `users.status` value of `suspended` is rejected with 401. The schema only defines `active` and `suspended`, not an `inactive` account state.
6. Successful login stamps `users.last_login_at`.
7. For `users.role = estate_owner`, `buildEstateOwnerPublicUser()` maps the DB role to `Estate Owner`, calls `UsersService.getEstateOwnerProfile()`, and requires both an owner profile and an estate to return a profile. No matching profile/estate is rejected with 401.
8. The service signs a payload containing `sub` (the string `users.id`) and `role` (`Estate Owner`).
9. The response is `{ accessToken, user: { id, name, role, phone, estate } }`. `accessToken` is a signed JWT. Password/hash values are not in the response.

`/auth/mobile/register` creates an `estate_owner` user and `tea_estate_owners` row, hashes the password with bcrypt cost 10, signs an Estate Owner JWT, and returns the same general `{ accessToken, user }` shape. It rejects duplicate phone/NIC with HTTP 409. Estate Owner registration through the Admin portal is a separate flow: the portal creates a `users` account with a random password hash; there is no password distribution/reset implementation in that flow.

### Tea Collector login: backend support already present

`POST /auth/agent/login` takes the same `{ phone, password }` body but calls `AuthService.agentLogin()`, not the generic login branch. It:

1. Looks up the shared user row by unique phone.
2. Verifies the submitted password against `password_hash` with `bcrypt.compare`.
3. Rejects a suspended user.
4. Requires `users.role === 'collection_agent'` and `AgentDirectoryService.byUserId(user.id)` to find an active HR employee of the Tea Collecting Agent job role linked to a collection-agent dispatch identity. Otherwise it returns 401 ("This account is not a collection agent.").
5. Stamps `last_login_at`.
6. Signs `{ sub: String(user.id), role: 'CollectionAgent' }`.
7. Returns `{ accessToken, agent: { id, name, phone }, mustChangePassword }`. The `agent.id` is `collection_agents.id`, while token `sub` is `users.id`.

The login response deliberately differs from `LoginResult`: it has `agent` and `mustChangePassword`, not `user`. The mobile `auth.api.ts` currently models only `LoginResult`, so it cannot accurately type/consume this endpoint yet.

### Password storage and initial credentials

- `users.password_hash` is a required text column. Runtime login compares a candidate password to it using `bcrypt.compare`; plaintext passwords are not stored.
- Owner self-registration hashes with `bcrypt.hash(..., 10)`.
- `AgentProvisioningService.provision()` generates a temporary password using `randomBytes(9).toString('base64url')`, hashes it at cost 10, creates the user with role `collection_agent`, and sets `must_change_password = true`. The generated value is returned once as `initialPassword` in the employee-create response; the code reviewed does not show a separate email/SMS delivery service.
- The Admin employee create/update flow provisions a login when the selected employee role is `Tea Collecting Agent`. `POST /employees` is the create endpoint, and `EmployeesService.create()` requires an Administrator. It first saves the HR row, calls provisioning, and removes the HR row if provisioning fails. Provisioning writes the user, factory employee subtype, collection-agent dispatch row, and employee-to-user link.
- Important schema/code mismatch to verify: `User.name` is non-null in `user.entity.ts` and `baseline.sql` (`name character varying(32) NOT NULL`), but `AgentProvisioningService.provision()` creates the User with phone, password hash, role, status, and temporary-password flag only; it does not supply `name`. Against that baseline, the user insert can fail at the database NOT NULL constraint. The agent provisioning unit test uses a mock repository and does not prove that this production insert succeeds.
- On the first agent sign-in, `mustChangePassword` is returned to the app. `POST /auth/agent/change-password` compares the current password, rejects reusing the same password, hashes the new one at cost 10, and clears `must_change_password`.
- Every protected agent-self-service operation calls `AgentSelfService.me()`, which checks that the user is not suspended and the temporary-password flag has been cleared. The check is per call, so deprovisioning/suspension and the first-password rule take effect despite an unexpired token.

### JWTs, guards, roles, expiration, and errors

- `AuthModule` requires `JWT_SECRET` and sets `expiresIn` from `JWT_EXPIRES_IN`, defaulting to `7d`. The actual environment values were not inspected or copied into this report.
- `JwtStrategy` extracts the JWT from the Authorization header, verifies signature and expiration (`ignoreExpiration: false`), then accepts only `Administrator`, `Officer`, or `Manager` from `PORTAL_ROLES`.
- `AgentJwtStrategy` uses a separate Passport strategy name (`jwt-agent`) and accepts only the `CollectionAgent` role claim. `AgentJwtGuard` protects the agent API.
- Both token types use the configured JWT secret. Separation is by the validated role claim and distinct guard/strategy, not by a configured JWT `aud` claim.
- `POST /auth/login` and `/auth/mobile/login` share `AuthService.login()`. That service explicitly handles `estate_owner` and `estate_manager`, and its default branch requires `toPortalRole()`. `collection_agent`, `receiving_officer`, and `plucking_employee` are not accepted through this generic branch.
- `toAppRole()` maps factory admin/officer/manager and estate owner/manager. `toPortalRole()` further restricts to the three factory roles. Neither maps Collection Agent or Receiving Officer.
- The API returns distinct 401 messages for unknown phone, wrong password, suspended account, missing profile, and unsupported role. This can reveal account/role state to a caller; consider a uniform public login error if that disclosure is not intended.
- `IdentityThrottlerGuard` is globally registered. The named `auth` throttler is configured for 5 requests per 60 seconds and its path filter covers `/auth/login`, `/auth/mobile/login`, and `/auth/mobile/register`; `/auth/agent/login` does not match that custom filter, although the global short/medium/long throttlers still apply. Verify whether agent login should receive the dedicated auth bucket.
- Portal `JwtStrategy` validates the signed token and role but does not reload the user's status. Thus a portal JWT already issued remains valid until expiry if the account is later suspended; the agent services do reload login status on every agent API call.
- There is no refresh-token endpoint or server-side JWT revocation/blacklist evident in the reviewed authentication code. Logout is therefore client-side token removal.

### Important authorization mismatch: mobile `/me`

`AuthMobileController.me()` uses `JwtAuthGuard`, which selects the `jwt` strategy. That strategy rejects every role outside `PORTAL_ROLES`, including `Estate Owner` and `Estate Manager`. Consequently, an Estate Owner can pass `/auth/mobile/login` and receive a token, but `/auth/mobile/me` will reject that token. The current mobile app does not call `/auth/mobile/me`, so this does not prevent the login screen from reporting success, but it blocks using this endpoint to restore/validate an estate-role session.

### Agent-only endpoints and ownership checks

`DispatchAgentController` is guarded at controller level by `AgentJwtGuard` under `/dispatch/me`. Its endpoints include:

- `POST /dispatch/me/shift/start`, `POST /dispatch/me/shift/end`
- `POST /dispatch/me/absence`, `DELETE /dispatch/me/absence`
- `POST /dispatch/me/pings`
- `GET /dispatch/me/cover-requests`
- `POST /dispatch/me/cover-requests/:id/accept`, `POST /dispatch/me/cover-requests/:id/decline`
- `GET /dispatch/me/stops`
- `POST /dispatch/me/push-token`

Each handler passes the JWT subject (`users.id`) into `AgentSelfService`. The service resolves the active agent using that subject before retrieving or mutating agent-specific data. This prevents a caller from supplying a different agent identity in these request paths. The portal-side `/dispatch/*` controller instead uses `JwtAuthGuard` and the server-driven `dispatch` permission level. Other application controllers also use `JwtAuthGuard`; Collection Agent tokens are rejected by that portal strategy.

## 2. End-to-end Estate Owner login flow

```text
Mobile app auth/login.tsx
  -> app/services/api/auth.api.ts login(phone, password)
  -> POST /auth/mobile/login
  -> AuthMobileController.login(LoginDto)
  -> AuthService.login(phone, password)
  -> UsersService.findByPhone(phone) -> users row
  -> bcrypt.compare(password, password_hash) + users.status check
  -> Estate Owner profile lookup: tea_estate_owners -> estates
  -> JwtService.sign({ sub: users.id, role: 'Estate Owner' })
  -> { accessToken, user }
  -> login screen persists accessToken/user
  -> router.replace('/(estate-owner)/home')
```

Frontend details:

- Screen: `source-code/mobile/src/app/auth/login.tsx`. It validates the phone via `getPhoneNumberError()` and requires a nonempty password. Failed API errors are routed to phone/password field messages where recognized, otherwise to a form-level message.
- Service: `source-code/mobile/src/app/services/api/auth.api.ts`; uses `/auth/mobile/login`.
- API URL: `source-code/mobile/src/app/services/api/client.ts` prefers `EXPO_PUBLIC_API_URL`; fallback uses the Expo dev host and port `3001`. Backend `main.ts` listens on the configured environment port and falls back to `3000`, so the deployment/dev environment must explicitly align these values. The actual runtime URL/port was not inspected.
- Persistence: native runtime writes `accessToken` and serialized `user` to Expo SecureStore keys of those names; web runtime writes them to `localStorage` with the same keys. There is no central session store or boot-time restoration in the reviewed mobile code.
- Navigation: successful Estate Owner login replaces the route with `/(estate-owner)/home`; Estate Manager routes to `/estate-manager`. The code has a redundant second Estate Owner check in the same handler. Other roles show "This account does not have a mobile dashboard yet."
- Logout: the Tea Collector demo profile only shows a confirmation alert; its "Log out" action does not clear stored credentials or navigate away. The estate-owner layout has no logout implementation in the reviewed file.
- Expired/invalid token handling: the mobile API client has no Authorization header and there is no token validation/401 cleanup path. It only parses a JSON response and throws `ApiError` for non-2xx results.
- Registration: `auth/register.tsx` calls `/auth/mobile/register`, but its `persistSession()` helper is not called after the registration result; it navigates to the Estate Owner home without persisting the returned JWT/user.

The Admin web portal has a separate factory-portal login integration, not an Estate Owner UI: `features/auth/LoginPage.tsx` posts phone/password through `services/auth.ts` to `/auth/login`, stores the token via `AuthContext`, and navigates to `/dashboard`. `lib/api.ts` uses `VITE_API_URL` (fallback `http://localhost:3000`), persists the JWT in `localStorage`, sets the Authorization header from the stored JWT on subsequent API requests, and notifies `AuthContext` on 401 so it logs out. `AuthContext` calls `/auth/me` on initial load and provides logout by clearing the token and user state. Its UI says "Sign in to the factory portal"; estate roles are not supported by the portal's protected API strategy.

## 3. Shared user and business-role structure

All implemented login identities use the shared `users` table. `users.role` is the DB role discriminator; the subtype/profile tables associate a login with its business record.

| User type | `users.role` | Profile/identity relationship found in code/schema | Login state found |
|---|---|---|---|
| Estate Owner | `estate_owner` | `tea_estate_owners.user_id` is unique FK to `users.id`; estates refer to `tea_estate_owners.id` through `estates.owner_id`. | Supported by generic/mobile login; no owner-specific token strategy. |
| Estate Manager | `estate_manager` | `users` -> `estate_employees.user_id` -> `tea_estate_managers.employee_id` and the managed estate. | Generic/mobile login maps the role and loads a manager profile. |
| Tea Collector / Collection Agent | `collection_agent` | `users` -> `factory_employees.user_id`; `collection_agents.employee_id` -> `factory_employees.id`; `collection_agents.hr_employee_id` -> `employees.id`; `employees.user_id` -> `users.id`. `AgentDirectoryService` treats an Active employee with job title `Tea Collecting Agent` and a linked login/agent identity as dispatchable. | Dedicated `/auth/agent/login`; temporary password and separate agent guard. |
| Receiving Officer | `receiving_officer` | `users` and `factory_employees` support the role; `receiving_officers.employee_id` links to `factory_employees`. | Role exists in schema but is not mapped by `toAppRole()` or accepted by either current login strategy. |
| Factory Admin | `factory_admin` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Administrator`. |
| Factory Manager | `factory_manager` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Manager`. |
| Factory Officer | `factory_officer` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Officer`. |
| Plucking Employee | `plucking_employee` | `users` -> `estate_employees.user_id`; plucking profile is separate. | Role exists but is not mapped by the reviewed auth role map. |

The HR `employees` table is separate from `factory_employees`; most employee rows have no login. For Collection Agents, both records are linked to the shared user identity. The `collection_agents` entity has no direct `user_id` property; account resolution goes through the HR/user links above. The existing Admin employee-registration process creates Tea Collector accounts. There is no separate public Collection Agent registration endpoint.

## 5. Mobile authentication and Tea Collector UI

### Existing reusable pieces

- Expo Router stack is configured in `source-code/mobile/src/app/_layout.tsx`.
- Existing phone/password form and field-level errors are in `app/auth/login.tsx`.
- `app/services/api/auth.api.ts` and `app/services/api/client.ts` provide a fetch service and basic API error type.
- SecureStore is already a dependency and the login screen persists access token and user data on native platforms.
- `components/ui/PasswordInput.tsx` and the existing password form can be reused.
- The backend agent endpoint, token strategy, password-change DTO, and dispatch endpoints are ready to be integrated.

### Existing limitations / not implemented

- `source-code/mobile/src/data/userRoles.ts` sends Estate Owner and Estate Manager to `/auth/login`, but sends "Factory Collector" directly to `/teacollector/teacollectorMobile`. That collector destination is a demo screen with hard-coded stops, requests, identity, and interface components; it is not an authenticated data-backed screen.
- The current login API calls `/auth/mobile/login`, whose generic login branch does not accept `collection_agent`. The correct backend login route is `/auth/agent/login`, and its response is `{ accessToken, agent, mustChangePassword }`, not `{ accessToken, user }`.
- `api/client.ts` uses `fetch`, not Axios; despite Axios being a package dependency, no Axios instance/interceptor is used by this authentication service. No Authorization bearer header is added by `apiRequest()`.
- There is no mobile `AuthContext` or Zustand auth store in the reviewed app code. `zustand` is installed but no authentication store use was found.
- No boot-time SecureStore read, `/auth/.../me` hydration, protected-route guard, or centralized 401/expired-token handling was found.
- The existing `auth/change-password.tsx` is a UI stub: its handler only logs fields and contains a TODO; it does not call `/auth/agent/change-password`. It is titled as a normal password change and its link says "Forgot password'" although no forgot-password API was found.
- The demo Tea Collector profile's logout button only presents a confirmation alert and does not clear session data.
- The Estate Owner/Manager token persistence code logs the submitted phone/password object and the returned access token to the JS console in `auth/login.tsx`. Remove such credential/token logging before production use.
- Mobile fallback API port is 3001, while backend default listen port is 3000. Use the actual environment's `EXPO_PUBLIC_API_URL`/`PORT` values to confirm connectivity; those runtime settings were not read.

## 7. Recommended implementation approach (analysis only; not implemented)

### Backend

1. Reuse `AuthService.agentLogin()`, `/auth/agent/login`, `AgentJwtStrategy`, and `AgentJwtGuard`; do not add another password table, JWT strategy, hashing utility, or generic login branch for agents.
2. Reuse the Administrator-only employee registration/update workflow to provision or re-enable accounts. Confirm the one-time `initialPassword` is conveyed to the collector through an approved secure operational channel.
3. Wire the mobile app to the existing agent-specific `/dispatch/me/*` endpoints. Continue deriving agent identity from the JWT subject; do not accept arbitrary agent/user IDs from the client for "my" operations.
4. Review whether agent login should be included in the dedicated auth rate-limit path. The current named auth bucket's path filter excludes `/auth/agent/login`.
5. Separately decide/fix the existing Estate Owner `/auth/mobile/me` guard mismatch before relying on that endpoint for Owner session hydration. Do not solve it by weakening the portal strategy to accept agent or estate roles.
6. Preserve role separation when adding routes: portal controllers use `JwtAuthGuard`; agent-self routes use `AgentJwtGuard`; service-level permission and subject ownership checks remain server-side.

Scope: Current source under source-code. This is a new appended investigation; earlier content above is preserved as-is and may describe older implementation states. No application source code was modified.

EXECUTIVE FINDINGS

The current end-to-end web/mobile code is more integrated than the older notes above: role selection routes Collection Agents to the shared mobile login, that screen calls POST /auth/mobile/login, and the backend's unified AuthService.mobileLogin() now supports collection_agent. A separate collector-login.tsx also exists and calls POST /auth/agent/login, but role selection does not use it.

The main operational blocker is in AgentProvisioningService.provision(): it creates a User without the required name field. The checked-in TypeORM User entity and backend baseline require users.name NOT NULL, while database/init.sql omits users.name and users.nic entirely. A real PostgreSQL provisioning test is needed; current tests use fakes and do not establish that the insert succeeds against the schema.

The password-change flow for the temporary Agent credential is implemented end-to-end. A separate generic “Forgot password / Change Password” screen is not implemented and logs entered passwords to the JavaScript console. After first change, the mobile app stores the token and opens the Collector screen, but that screen remains demo/static and does not make authenticated calls. There is no Collector session restoration, route guard, or functioning logout.

1. COLLECTION AGENT CREATION: ADMIN FORM TO DATABASE

Admin entry point and form

The dashboard's New Employee quick action leads to /employees/new; the employee list has an Add Employee action to the same route. App.tsx registers EmployeeRegistrationPage at that path. The form collects the HR record fields, dynamically loads valid job titles, and treats the Tea Collecting Agent job title specially: it explains that a mobile login is created, forces the login toggle on visually, and submits the completed EmployeeForm.

useEmployeeRoles() fetches GET /employees/roles. EmployeesController.roles() returns the backend role list and agentRole value, so the form does not locally define which title triggers provisioning. The server-side AGENT_JOB_ROLE constant is "Tea Collecting Agent".

The form mutation calls employeesService.create(data). The frontend service POSTs JSON to /employees using the portal apiFetch wrapper. apiFetch attaches the current factory-portal JWT as Authorization: Bearer, so the create call reaches the guarded employee API as the logged-in portal user. When the returned Employee has initialPassword, the page keeps the response in component state and opens InitialPasswordModal; otherwise it navigates directly to the employee detail.

Backend controller and authorization

EmployeesController is guarded by JwtAuthGuard at controller level. POST /employees receives CreateEmployeeDto, resolves the actor name and role from the request JWT, and delegates to EmployeesService.create(). The same controller's PUT /employees/:id uses EmployeesService.update() for role changes to/from Tea Collecting Agent.

CreateEmployeeDto validates required name/NIC/contact/address/role, date fields, bank data, employment type, login toggle and optional pay rates. It validates the contact against a Sri Lankan phone pattern and role against EMPLOYEE_ROLES. The global ValidationPipe in main.ts enables whitelist validation. Age >= 18 and non-future hire date are checked in EmployeesService rather than the DTO.

EmployeesService.create():
- Requires actor.role === Administrator via assertIsAdmin(); an Officer or Manager cannot create the roster entry.
- Checks date constraints and duplicate employee NIC.
- If dto.role is AGENT_JOB_ROLE, checks that dto.contact is not already attached to a User login before saving the HR record.
- Saves an EmployeeEntity with userId initially null and status Active.
- Calls AgentProvisioningService.provision(saved) for the agent role. If this call fails, it attempts to delete the just-saved HR row and rethrows. It records an audit event only after the save/provision succeeds.
- Returns the public employee fields plus initialPassword only when provisioning returned a non-null password.

AgentProvisioningService.provision():
- Executes the login/dispatch identity writes in a DataSource transaction.
- If a collection_agents identity already exists for the HR employee, it re-enables the linked User (when employee.userId is set) and returns initialPassword: null. This preserves the existing login and history; no new credential is displayed.
- For a new identity, checks the phone again inside the transaction, selects the first Factory, and fails if no factory exists.
- Generates and hashes the temporary password, saves a users row, inserts factory_employees with the HR employee's name/NIC and role collection_agent, creates collection_agents linked to the factory employee and HR employee, then saves employees.userId and hasLogin = true.
- Returns the one-time plaintext password to EmployeesService. The employee response type includes optional initialPassword; ordinary employee serialization does not derive it from a stored field.

2. TEMPORARY PASSWORD AND FRONTEND DISPLAY

The password generation is randomBytes(9).toString('base64url') in AgentProvisioningService.provision(). Nine cryptographically random bytes represent 72 bits of entropy and encode to 12 base64url characters. The exact generated value is passed to bcrypt.hash(initialPassword, 10); bcrypt creates the salted hash at cost 10. Only the resulting string is assigned to users.password_hash. The original password is not assigned to a User/Employee/Agent database property.

The plaintext follows this response path:
AgentProvisioningService.provision() return value
  -> EmployeesService.create() or update() includes initialPassword in PublicEmployee
  -> EmployeesController returns JSON from POST /employees or PUT /employees/:id
  -> employeesService.create()/update() frontend resolves the JSON as Employee
  -> EmployeeRegistrationPage or EmployeeEditPage retains it briefly in React state
  -> InitialPasswordModal renders and optionally copies it.

Yes, the frontend displays it. InitialPasswordModal shows the phone and password, marks it as shown once, and includes a copy-to-clipboard button. The admin is expected to pass the password to the Agent; no email/SMS delivery flow was found. Once the modal/page state is discarded there is no endpoint to recover the plaintext. If an Agent is re-enabled using an existing identity, provision() returns null, so the UI does not show a new password.

Security implication: the one-time password is intentionally present in the authenticated admin API response and frontend memory. It must be transmitted to the admin only over TLS in production and handed to the Agent through an approved private channel. Browser/network/proxy response-body logging, screenshots and clipboard exposure should be considered. There is no expiration timestamp or temporary-password consumption counter; the account remains in must-change state until the Agent changes it.

3. FIRST-TIME LOGIN THROUGH /auth/mobile/login

Navigation and frontend request

The role picker uses /auth/login for Collection Agent. MobileLoginForm collects phone/password, validates that the phone looks valid and password is nonempty, and calls its onSubmit handler. login.tsx calls login(phoneNumber, password) from the mobile auth API module. That function POSTs { phone, password } to /auth/mobile/login. The response type is a union of LoginResult and AgentLoginResult; the client discriminates the Agent shape with "agent" in result.

Controller and service verification

AuthController.mobileLogin() accepts LoginDto and calls AuthService.mobileLogin(phone, password). AuthService.mobileLogin():
- Finds the User by phone.
- Rejects roles other than estate_owner, estate_manager, or collection_agent.
- Routes collection_agent accounts to agentLoginWithUser(); other supported mobile roles use the general loginWithUser() path.

agentLoginWithUser():
- bcrypt.compare(password, user.password_hash) verifies the submitted credential; the plaintext is not queried or stored.
- Rejects users.status = suspended.
- Requires role collection_agent and AgentDirectoryService.byUserId(user.id) to resolve an active HR Employee with the Tea Collecting Agent title, linked user id, and collection_agents dispatch identity. An inactive employee, changed job title, missing identity, or missing link is rejected.
- Calls UsersService.markLogin() to update users.last_login_at.
- Signs an AgentJwtPayload with sub = the User id and role = CollectionAgent.
- Returns accessToken, agent {id, name, phone}, and mustChangePassword copied from users.must_change_password.

must_change_password behavior:
- The initial flag is true for a new provisioned user and is returned as mustChangePassword. AuthService does not refuse to issue the JWT solely because the flag is true.
- The mobile client sees the flag and routes to the temporary-password screen rather than the dashboard.
- More importantly, agent data endpoints are guarded by AgentJwtGuard and their AgentSelfService methods resolve the caller through the JWT subject. AgentSelfService.me() rechecks HR active/role/link, user suspension and mustChangePassword on every protected operation. Thus the login token cannot perform dispatch actions while the password is still temporary.

There are two agent login endpoints in the current tree. The role-selected main app uses /auth/mobile/login. The separate CollectorLoginScreen uses loginAgent() and /auth/agent/login, which calls AuthService.agentLogin() and then the same agentLoginWithUser() credential logic. The dedicated screen is not the route configured in userRoles.ts.

4. TEMPORARY PASSWORD CHANGE

The shared login screen stores the access token and agent details as a pending Collector session if mustChangePassword is true, then routes to /auth/collector-change-password. The dedicated collector-login.tsx screen does the same. The password screen loads collectorPendingSession and validates current password, new password (8–72 characters), new != current, and confirmation equality before submitting.

The frontend changeAgentPassword() method POSTs currentPassword and newPassword to /auth/agent/change-password. Unlike the general mobile apiRequest() client, this one explicitly sets Authorization: Bearer <agent token>.

AuthController.changeAgentPassword() is guarded by AgentJwtGuard, gets the numeric User id from the verified JWT subject, and passes the two fields to AuthService.changeAgentPassword(). ChangePasswordDto requires a string/nonempty current password and string new password of 8–72 characters. The backend does not receive a confirmation field; equality confirmation exists only in the UI.

AuthService.changeAgentPassword():
- Loads the User by JWT id and requires users.role = collection_agent.
- Verifies currentPassword using bcrypt.compare().
- Rejects using the same current and new plaintext password.
- Hashes newPassword with bcrypt.hash(newPassword, 10).
- Calls UsersService.setPassword(userId, hash).

UsersService.setPassword() performs one update setting password_hash to the new bcrypt hash and must_change_password = false. It returns no password/hash to the client. The password screen then calls completeCollectorSession() and routes to /teacollector/teacollectorMobile. If the backend changed the password but writing the completed session fails, the UI instructs the user to sign in again using the new password.

The endpoint is authenticated and verifies the current password, but it does not recheck user.status or current active HR-agent membership. The protected dispatch API still blocks suspended/inactive agents through AgentSelfService; the password-change endpoint itself can still change a suspended agent's password if a previously issued valid agent token and current password are presented.

5. SESSION STORAGE, DASHBOARD AND FUTURE LOGINS

On successful login with no forced change, or after password change, completeCollectorSession() constructs a profile with role CollectionAgent and stores:
- accessToken under "accessToken";
- serialized agent profile under "user";
- removes "collectorPendingSession".

Native platforms use expo-secure-store. Web uses localStorage. The pending password-change flow stores its token/profile under collectorPendingSession until completion.

login.tsx replaces navigation with /teacollector/teacollectorMobile after session completion. The dashboard component currently initializes stops and fertilizer requests from hard-coded demo arrays, and even displays a fixed greeting. It does not retrieve the JWT or use authenticated /dispatch/me/* data. The mobile API client has no automatic bearer-token attachment; only the password-change function manually supplies Authorization.

After changing the password, the current JWT is kept; the server does not rotate it. On a subsequent sign-in, the new password matches the new hash, AuthService returns mustChangePassword = false, the app completes the session directly and enters the dashboard. The old temporary password no longer matches. Agent JWTs use the configured shared JWT_SECRET and configured expiration (JWT_EXPIRES_IN, default 7d); the agent strategy checks the CollectionAgent role claim and expiration, but the strategy is not a revocation list. No refresh or token-revocation flow was found.

6. ISSUES AND SECURITY CONCERNS

P1 — provisioning User insert is incompatible with required schema:
AgentProvisioningService.provision() creates User without name. User.name is a non-null TypeORM column; backend/src/migrations/baseline.sql also has users.name VARCHAR(32) NOT NULL. On that baseline, a new agent insert fails and the transaction rolls back. The employee create flow then attempts to delete the HR row.

The fresh database schema is also inconsistent: database/init.sql creates users without name and nic, but User maps both fields. The 2026-10-10-agent-employees.sql migration adds must_change_password and collection_agents.hr_employee_id, not users.name/nic. Since AppModule configures TypeORM synchronize:false, the application will not repair this automatically. A database made only from current init.sql is incompatible with the User entity. The actual runtime database was not inspected.

Even when assigning the employee name to User, EmployeeEntity permits name up to 100 characters while User.name is varchar(32); the Employee DTO has no matching max-length check. Reconcile column lengths and validation rather than simply copying arbitrary-length names.

P1 — changing an existing employee to Agent can strand the record:
EmployeesService.update() saves the HR role before provision() but unlike create() has no try/catch/transaction restoring the prior employee on failure. If provisioning fails, the employee remains Active with the Agent title. On the next update, wasAgent becomes true based on the saved role/status, so the update takes syncContact() rather than retrying provision(). This can leave an Active HR Agent with no user/dispatch identity and no normal retry path.

P1 — Collector “Forgot password” is not a working recovery flow and logs credentials:
The main role-selected login uses MobileLoginForm defaults, which show Forgot password and registration links for all roles. The Forgot password link opens the generic auth/change-password.tsx stub. Its button handler logs currentPassword, newPassword and confirmPassword to console and contains a TODO rather than calling an API. No Collector password reset/recovery endpoint or safe delivery mechanism was found. A dedicated collector-login screen hides those links, but it is not the route selected by userRoles.ts.

P1 — dashboard/session lifecycle incomplete:
The Collector dashboard remains demo/static and is not connected to agent APIs. The app lacks startup restoration/hydration of saved Collector credentials, protected navigation, central bearer injection, expiry/401 cleanup, and a real logout. The displayed demo profile logout action only presents an alert. A stored token therefore does not currently make the screen a functional authenticated Collector experience.

P2 — mobile default API port differs from backend:
mobile/src/app/services/api/client.ts defaults to port 3001; backend/src/main.ts defaults to 3000. Unless EXPO_PUBLIC_API_URL or environment configuration aligns them, the mobile auth request cannot reach the default local backend.

P2 — password-change endpoint state checks and token lifecycle:
changeAgentPassword() validates User existence/role/current password but not suspended status or active Employee linkage. A previously issued token remains usable for password change after suspension/deactivation, though agent data operations remain blocked. Password change also does not rotate/revoke existing JWTs. Consider consistent state checks and explicit session invalidation/rotation policy.

P2 — JWT separation relies on role, not audience:
AgentJwtStrategy and the portal strategy use JWT_SECRET; the agent strategy accepts role CollectionAgent and the portal strategy accepts portal roles. This guards role crossover, but there is no distinct aud claim/secret. Preserve strict role checks and consider explicit issuer/audience separation if the token boundary is a security requirement.

P2 — throttling differs by endpoint:
POST /auth/mobile/login skips short/medium/long throttler buckets but still matches the dedicated auth bucket configured for 5 attempts per 60 seconds. POST /auth/agent/login does not match that custom auth path filter and only has the general short/medium/long limits. The primary mobile route has the dedicated limit, but the alternate login endpoint should receive a deliberate equivalent policy or be retired.

P2 — login response allows account/role enumeration:
Unknown phone, wrong password, suspended account, and non-Agent account produce distinguishable responses. Review whether an external caller should be able to infer account and role state.

### 1. Session persistence and restoration

**Session persistence — Partially Implemented.** `source-code/mobile/src/utils/collectorSession.ts` (`completeCollectorSession`, `setStoredValue`, `storePendingCollectorSession`) serializes a Collector profile and token after ordinary Agent login and after successful temporary-password change. Native platforms use `expo-secure-store`; the web branch uses `localStorage`, which does not provide equivalent protection against script access. During forced password change, `collectorPendingSession` is stored separately and later promoted to the completed session.

The completed Collector session uses the generic keys `accessToken` and `user`, not Collector-specific keys. `source-code/mobile/src/app/auth/login.tsx` (`persistSession`) writes Estate Owner/Manager sessions to those same keys. `source-code/mobile/src/app/auth/register.tsx` also defines the same persistence scheme, although its current submit handler discards the registration response rather than calling that helper. This means the app has persistence primitives, but not a role-aware, independently managed session store.

Why the gap matters: restoring the wrong role from shared storage can expose the wrong UI, and clearing a Collector session must not accidentally destroy an Estate Owner/Manager session. The current exact-role check mitigates profile confusion but does not protect the routes.

Recommended approach: evolve the existing `collectorSession.ts` rather than introduce another authentication utility. Define a typed Collector session read/write/clear contract, handle storage writes as one logical operation, and ensure invalidation only removes the Collector session. Preserve the Estate Owner/Manager flows by either using role-specific keys or a shared, explicitly role-tagged session abstraction with role-aware ownership. Keep native credentials in SecureStore; do not describe the web `localStorage` branch as secure storage.

**Startup retrieval — Not Implemented.** `source-code/mobile/src/app/_layout.tsx` (`RootLayout`) configures an Expo Router `Stack` but has no loading/auth state or guard. `source-code/mobile/src/app/index.tsx` (`SplashScreen`) waits 500 ms and unconditionally calls `router.replace("./(onboarding)")`. No startup call to `getCollectorProfile()` or a session-restoration function was found.

Why the gap matters: the token written by login is never consulted at app launch, so closing/restarting the app loses the authenticated navigation state even if storage still contains the token.

Recommended approach: add a single bootstrap decision at the existing root/router boundary, reusing the session utility. Hold rendering/navigation behind a loading state while the saved Collector session is read and checked; route valid sessions to the Collector home and absent/invalid sessions to the appropriate role/login flow. Do not treat a locally present token as server-validated.

**Automatic restoration and dashboard navigation — Not Implemented.** `source-code/mobile/src/app/teacollector/teacollectorMobile.tsx` (`TeaCollectorMobile`) calls `getCollectorProfile()` in a `useEffect` only to populate profile display text. A missing profile sets `profileUnavailable`; it does not stop rendering, establish auth state, or navigate to login. Successful navigation to `/teacollector/teacollectorMobile` occurs only in the login handlers and after password change.

Why the gap matters: there is no distinction between a restored, authenticated session and a demo screen rendered without any session.

Recommended approach: make restoration produce an explicit boot/auth state (loading, authenticated Collector, unauthenticated, or temporarily unverifiable). Render the Collector app only for the authenticated state and navigate only after restoration is complete. Keep the existing login/password-change route behavior, but use the same session state after successful completion.

**Missing, corrupted, expired session behavior — Partially Implemented; cleanup is Not Implemented.** `getCollectorProfile()` returns `undefined` if the token/profile is missing, if parsed profile JSON is not an object, or if its role is not `CollectionAgent`. It catches malformed profile JSON and returns `undefined`, but does not remove either storage key. `getPendingCollectorSession()` calls `JSON.parse()` without a syntax-error recovery or cleanup; `collector-change-password.tsx` (`loadSession`) displays the resulting error, but leaves the bad pending value stored. An expired JWT is not decoded or checked by the client. The backend rejects expiration when an API request is made, but the mobile client does not respond by clearing storage.

Why the gap matters: stale or malformed state can cause repeated broken boots, and a locally expired token can still leave Collector screens visible. Client-side expiry checks alone cannot detect suspension or Agent deactivation.

Recommended approach: validate the saved object shape and token expiry for early rejection, and remove invalid Collector data through the same clear helper. For authoritative validation, use a small Agent-session endpoint guarded by the existing `AgentJwtGuard` and backed by the same active-Agent/account checks as `AgentSelfService.me()`. Treat 401/403 as definitive invalidation; treat network failure separately from invalid credentials so an outage does not silently erase a potentially valid session. If offline restoration is supported, explicitly limit it to the app's documented offline capabilities.

### 2. Protected navigation and role separation

**Route protection, redirects, and direct navigation — Not Implemented.** `RootLayout` has no authentication check, and there is no Collector-specific `_layout.tsx` or route guard under `source-code/mobile/src/app/teacollector/`. `teacollectorMobile.tsx` is an Expo Router route, and the `demo-teacollector-*.tsx` files are also under the `app` route tree; they contain no authentication checks. The demo profile's logout button in `demo-teacollector-profile.tsx` only opens a confirmation alert and does not clear credentials or navigate away. The dedicated `collector-login.tsx` screen is present, but having a login screen is not a redirect/guard.

Why the gap matters: an unauthenticated user can navigate directly to the dashboard route (or another route in the Collector route tree) without passing through login. Protecting only the first dashboard screen would still leave sibling routes accessible through a deep link.

Recommended approach: add a common Collector-only layout/guard for every protected Agent route, including any future nested screens, and check route state before rendering content. Keep Collector login and the temporary-password screen outside the protected group; the latter should require a valid pending Agent session. When unauthenticated or invalid, replace the current route with Collector login to avoid returning to the protected screen via Back. Test both in-app navigation and direct URL/deep-link entry.

**Expired/invalid token screen access — Partially Implemented at API boundary only.** `AgentJwtStrategy` rejects bad signatures, invalid claims, and expired JWTs; however, no UI route checks a token, and `apiRequest()` does not attach the saved token automatically. Presently the Collector UI is demo-backed, so opening the dashboard does not even force a protected request. Thus the backend protects operations, not the mobile screen.

Why the gap matters: a user can continue viewing and interacting with a stale/demo screen, and once live requests are added, individual request handlers could each mishandle 401/403 differently without a shared boundary.

Recommended approach: combine local route gating with a single authenticated API client. Local `exp` checking is a usability optimization only; backend validation remains authoritative. On a server-confirmed 401/403, clear the Collector session and redirect once to login; avoid redirect loops on login/password-change endpoints.

**Estate Owner/Manager conflict — Partially Implemented.** `getCollectorProfile()` only returns a profile when stored `user.role === "CollectionAgent"`, so a normally stored Estate Owner/Manager profile is not displayed as a Collector profile. On the backend, `AgentJwtStrategy.validate()` requires the exact Agent role. However, generic Estate sessions and Collector sessions share `accessToken` and `user`; a role switch overwrites the previous account's values. Also, because the Collector UI has no guard, an Estate Owner/Manager can still open the Collector route and see its hard-coded demo content even though their token cannot authorize Agent APIs.

Why the gap matters: role-specific navigation must not rely on a profile display check, and a Collector logout/session expiry must not clear or misroute an Estate Owner/Manager session.

Recommended approach: have the route guard require an explicitly validated `CollectionAgent` session, not merely a non-empty token or profile. Keep Estate Owner/Manager login and navigation unchanged, and make storage ownership/clearing role-safe. Do not treat either estate role's JWT as an Agent JWT.

### 3. Backend authentication, token validation, and unauthorized responses

**Collector JWT issuance — Implemented.** `source-code/backend/src/auth/auth.controller.ts` exposes `POST /auth/agent/login` and the unified `POST /auth/mobile/login`. `AuthService.mobileLogin()` dispatches `collection_agent` accounts to `agentLoginWithUser()`; the dedicated endpoint calls the same method through `agentLogin()`. `agentLoginWithUser()` checks the password hash and suspension state, requires an active Agent identity through `AgentDirectoryService`, stamps login time, and signs `{ sub: String(user.id), role: AGENT_ROLE }`. It returns `{ accessToken, agent, mustChangePassword }`. The mobile clients use these Agent endpoints (`auth.api.ts` `loginAgent`; `login.tsx` uses unified mobile login and discriminates the Agent result).

**JWT expiration — Partially Implemented.** `source-code/backend/src/auth/auth.module.ts` registers `JwtModule` with `JWT_EXPIRES_IN`, defaulting to `7d`. Both portal and Agent tokens use this same module configuration. `AgentJwtStrategy` sets `ignoreExpiration: false`, so Passport JWT verifies standard expiry claims and rejects expired tokens. The configured runtime environment value was not inspected; therefore the effective deployed duration cannot be confirmed from this review.

Why the gap matters: local restoration needs an expiry-aware experience, but the deployed lifetime also determines how long a stolen token could remain usable. A mobile client must not assume the default if the environment overrides it.

Recommended approach: retain backend expiry enforcement, document/configure the deployment value deliberately, and have restoration handle expired-token 401 responses by clearing the Collector session. Do not add a separate client-side lifetime that can diverge from the backend.

**Protected Agent endpoints and guard usage — Implemented.** `AgentJwtStrategy` (`auth/agent-jwt.strategy.ts`) extracts Bearer JWTs, verifies using `JWT_SECRET`, rejects expired tokens, and accepts only `CollectionAgent`. `AgentJwtGuard` selects the named `jwt-agent` strategy. It is applied at controller level to `DispatchAgentController` (`/dispatch/me/*`), `FertilizerAgentController` (`/dispatch/me/fertilizer/*`), and to `AuthController.changeAgentPassword()` (`/auth/agent/change-password`). `AgentSelfService.me()` additionally resolves the subject to the active HR Agent/dispatch identity and checks current account suspension and `must_change_password` state for dispatch operations. Consequently a valid signature alone does not let a non-Agent use these guarded APIs.

Boundary note: `AgentJwtStrategy` performs JWT/role validation, while active HR status and temporary-password checks occur in Agent service calls, not in the strategy itself. The password-change handler is also Agent-guarded, but the previously documented `AuthService.changeAgentPassword()` does not recheck suspension or active HR membership. That does not negate JWT expiry validation, but it is a separate account-state consistency limitation.

**Role/audience isolation — Implemented for roles; no separate cryptographic audience.** The Agent strategy accepts the exact `CollectionAgent` claim. `JwtStrategy` for the portal rejects `CollectionAgent` and any role outside `PORTAL_ROLES`. `AuthService.agentLoginWithUser()` also requires the database role `collection_agent` and an active directory record at login. Agent services resolve ownership from JWT `sub`, rather than trusting a client-supplied Agent id. Both strategies use `JWT_SECRET`; no distinct `aud`/issuer or Agent-specific secret was found. Estate Owner/Manager tokens therefore fail the Agent strategy's role check, and Agent tokens fail the portal strategy's role check, but isolation is claim-based.

Why the gap matters: keeping distinct audiences prevents cross-role tokens from being accepted as the mobile app adds more endpoints. The existing role boundary is working; a separate audience/secret is a defense-in-depth design choice rather than a prerequisite for the current guard behavior.

Recommended approach: preserve the existing Agent login, `AgentJwtStrategy`, and `AgentJwtGuard`; do not create a second Collector authentication system. Consider explicit issuer/audience restrictions only as a deliberate backend token-boundary hardening change, updating all issuers and validators together.

**Mobile 401/403 handling — Not Implemented.** `source-code/mobile/src/app/services/api/client.ts` (`apiRequest`) sends JSON requests and throws `ApiError` when `response.ok` is false. `ApiError` retains messages but not HTTP status; there is no global interceptor, saved-token attachment, expiry cleanup, role-aware redirect, or shared 401/403 handling. `changeAgentPassword()` in `auth.api.ts` is the only inspected mobile call that explicitly supplies `Authorization: Bearer ...`; the general `apiRequest()` does not add a token. The Collector dashboard currently makes no Agent API calls, so unauthorized responses cannot currently drive session state.

Why the gap matters: when the demo UI is replaced with protected dispatch/fertilizer data, errors could be shown as ordinary form failures while stale credentials and protected navigation remain active.

Recommended approach: extend the existing API client to accept/use the current Collector token for Agent calls and preserve HTTP status in `ApiError`. Centralize 401/403 handling in the session/auth boundary: clear and redirect for authentication/authorization failures according to the chosen role policy, while preserving ordinary validation errors and distinguishing network/offline failures. Avoid independently implementing token/error handling in each screen.

### 4. Recommended implementation sequence

1. **Define the role-safe session contract** by extending `collectorSession.ts`: typed read, write, and clear behavior; shape validation; safe handling of corrupt pending/completed data; and no accidental deletion of Estate Owner/Manager credentials. Keep SecureStore for native storage.
2. **Add authoritative Agent session validation** using the existing Agent JWT path (`AgentJwtGuard` and Agent identity/account checks). Ensure it returns enough verified profile data for restoration without exposing a generic estate/portal token as an Agent session.
3. **Implement app bootstrap/restoration** at the existing root/splash boundary. Show a loading state, read saved Collector state, reject locally expired/corrupt state, validate it with the backend when online, and navigate to the Collector dashboard only when accepted. Specify offline behavior separately from server-confirmed authentication.
4. **Protect the complete Collector route tree** with a shared Expo Router layout/guard. Include the dashboard and all Collector-only routes; leave login and pending-password-change routes accessible under their respective conditions. Verify direct URLs, back navigation, and deep links.
5. **Integrate the API client and invalidation flow**: attach the Collector bearer token to Agent API calls, retain status codes, clear the Collector session and redirect on confirmed 401/403, and leave session state intact on transient connectivity failures where appropriate.
6. **Replace placeholder logout/profile behavior** with real Collector session clearing and role-safe navigation. Do not let logout affect an Estate Owner/Manager session.
7. **Add focused tests** for native/web session serialization and malformed data, role crossover, startup routing, direct protected-route access, expired-token cleanup, 401/403 handling, and backend Agent guard/account-state behavior. Include Estate Owner/Manager regression coverage for shared navigation and storage.

This analysis is based on the source paths and methods named above. The backend's configured signing secret and actual `JWT_EXPIRES_IN` value were not read, and no live device/backend session was exercised.

### Execution flow and implementation details

1. `src/app/auth/login.tsx` keeps the shared mobile login and role-based routing. A successful Collector login is persisted through `src/utils/collectorSession.ts`; a temporary-password result is persisted as a pending session instead. Estate Owner/Manager login marks its role as active without removing the separately stored Collector session.
2. `src/context/CollectorAuthContext.tsx`, mounted by `src/app/_layout.tsx`, starts in `checking`. It reads the active role and the relevant saved Collector session. Local JWT decoding is only a fast check for the expected `CollectionAgent` role and a future `exp`; it does not verify the JWT signature.
3. Before marking a saved session authenticated, the provider calls `validateAgentSession()` in `src/app/services/api/auth.api.ts`, which requests `GET /auth/agent/session`. The backend validates the signature, expiration and Agent role through the existing `AgentJwtGuard` / `AgentJwtStrategy`, and `AuthService.agentSession()` checks the persisted account and active Agent relationship. The server-provided Agent profile is used for the restored session.
4. `src/app/index.tsx` routes a confirmed Agent to `/teacollector/teacollectorMobile`; a session requiring a password change goes to `/auth/collector-change-password`. During checking, Collector content is not rendered. A transient connectivity failure shows a retry notice and retains the saved session rather than treating an unverified token as authenticated.
5. `src/app/teacollector/_layout.tsx` is the route-tree boundary. It renders child routes only for `authenticated`, routes unauthenticated users to `/auth/login`, and sends pending-password sessions to the existing password-change flow. This protects deep links as well as navigation from the splash screen.
6. `src/app/services/api/client.ts` adds status/code-aware `ApiError` handling and the Agent-only `agentApiRequest()` helper. Ordinary Estate Owner/Manager `apiRequest()` calls retain their prior behavior. The Agent helper clears a Collector session on 401 and on the explicit `AGENT_SESSION_INVALID` / `AGENT_PASSWORD_CHANGE_REQUIRED` 403 codes; unrelated permission 403s are not interpreted as expired credentials. The password-change-required case transitions the saved session into the pending-password flow.
7. `src/app/teacollector/teacollectorMobile.tsx` and `demo-teacollector-profile.tsx` use the shared Collector auth/logout path rather than treating local demo state as authentication. `collector-login.tsx` and `collector-change-password.tsx` integrate with the same session context and storage utility; no parallel authentication store was added.
