# Authentication Architecture Analysis

Repository review date: 2026-11-08
Scope: source-code only; no authentication or schema changes made.

## Executive summary

- Estate Owner authentication is implemented in the mobile app and backend. The mobile login screen calls `POST /auth/mobile/login`; the shared `AuthService.login()` authenticates the `users` row and returns a JWT plus an Estate Owner profile.
- Tea Collector authentication is already implemented on the backend, contrary to what an earlier project-status note might suggest. `POST /auth/agent/login` verifies a Collection Agent login and returns an agent-specific JWT and a `mustChangePassword` flag. The Admin employee-registration path attempts to provision the login and return a one-time temporary password, but there is a likely missing required `users.name` value in the provisioning insert (details below).
- The mobile app is not integrated with this Tea Collector backend flow. The role selector sends "Factory Collector" to a mock screen; its login service calls `/auth/mobile/login`, not `/auth/agent/login`. The mobile API client does not attach bearer tokens, and there is no mobile auth context, protected-route/session-restoration flow, or implemented logout.
- Agent API security is implemented: agent tokens and portal tokens are accepted by separate Passport strategies, and `dispatch/me/*` resolves the current agent from the JWT subject and checks current employee/login status and the temporary-password flag on each call.
- A relevant existing mismatch: `/auth/mobile/me` uses the portal `JwtAuthGuard`, whose strategy accepts only Administrator/Officer/Manager tokens. An Estate Owner or Estate Manager can get a successful login token, but that token is rejected by this guard. This route is not usable by the estate-role mobile session as currently written.
- No new database table appears necessary for Tea Collector login if the current schema and migration are applied. The needed `users`, `factory_employees`, `employees`, and `collection_agents` relationships and temporary-password column are already represented. However, the TypeORM entity and DB baseline require `users.name`, which agent provisioning does not supply, and tracked `init.sql` omits `users.name`/`users.nic`; a fresh-database setup and real provisioning should be verified before depending on the flow.

## 1. Backend authentication architecture

Authentication is implemented with NestJS, Passport JWT, TypeORM, `bcrypt`, and `@nestjs/jwt`. There is no custom `@Roles` or `@CurrentUser` decorator in the authentication path: route protection uses Nest `@UseGuards(...)`, and role/permission checks are performed in strategies or services. `@SkipThrottle` is used on selected login routes.

### Login endpoints and request bodies

| Endpoint | Method | Body / DTO | Purpose |
|---|---|---|---|
| `/auth/login` | POST | `LoginDto`: JSON object with phone and password fields | Shared login entry point, used by the Admin portal service. |
| `/auth/mobile/login` | POST | Same `LoginDto` | Mobile owner/manager login. Calls the same `AuthService.login()` as `/auth/login`. |
| `/auth/mobile/register` | POST | `RegisterDto`: `name`, `phone`, `nic`, `password`, `confirmPassword` | Public Estate Owner registration. |
| `/auth/agent/login` | POST | Same `LoginDto` | Tea Collector login. Calls the separate `AuthService.agentLogin()`. |
| `/auth/agent/change-password` | POST | `ChangePasswordDto`: `currentPassword`, `newPassword` | Agent-only first password change, guarded by `AgentJwtGuard`. |
| `/auth/me` | GET | Authorization header containing JWT | Portal profile; guarded by `JwtAuthGuard`. |
| `/auth/mobile/me` | GET | Authorization header containing JWT | Mobile profile handler; currently also guarded by `JwtAuthGuard`, so it accepts portal roles only (see the role-strategy issue below). |

`LoginDto` checks that `phone` is a string and that password length is at least one; it does not apply the stricter Sri Lankan phone-number format used by registration. `RegisterDto` checks an LK phone number, a valid old/new Sri Lankan NIC pattern, a password of at least eight characters, and matching confirmation. `ChangePasswordDto` checks a nonempty current password and an 8-72 character new password. `main.ts` enables `ValidationPipe({ whitelist: true })`; validation properties not declared in a DTO are stripped.

### Estate Owner login: verified backend sequence

1. The mobile frontend posts `{ phone, password }` to `/auth/mobile/login`.
2. `AuthMobileController.login()` passes both values to `AuthService.login()`.
3. `UsersService.findByPhone()` looks up the unique `users.phone`.
4. `AuthService.login()` returns HTTP 401 (`UnauthorizedException`) if there is no matching user; otherwise it runs `bcrypt.compare(password, user.password_hash)`. A mismatch also returns 401.
5. A `users.status` value of `suspended` is rejected with 401. The schema only defines `active` and `suspended`, not an `inactive` account state.
6. Successful login stamps `users.last_login_at`.
7. For `users.role = estate_owner`, `buildEstateOwnerPublicUser()` maps the DB role to `Estate Owner`, calls `UsersService.getEstateOwnerProfile()`, and requires both an owner profile and an estate to return a profile. No matching profile/estate is rejected with 401.
8. The service signs a payload containing `sub` (the string `users.id`) and `role` (`Estate Owner`).
9. The response is `{ accessToken, user: { id, name, role, phone, estate } }`. `accessToken` is a signed JWT. Password/hash values are not in the response.

`/auth/mobile/register` creates an `estate_owner` user and `tea_estate_owners` row, hashes the password with bcrypt cost 10, signs an Estate Owner JWT, and returns the same general `{ accessToken, user }` shape. It rejects duplicate phone/NIC with HTTP 409. Estate Owner registration through the Admin portal is a separate flow: the portal creates a `users` account with a random password hash; there is no password distribution/reset implementation in that flow.

### Tea Collector login: backend support already present

`POST /auth/agent/login` takes the same `{ phone, password }` body but calls `AuthService.agentLogin()`, not the generic login branch. It:

1. Looks up the shared user row by unique phone.
2. Verifies the submitted password against `password_hash` with `bcrypt.compare`.
3. Rejects a suspended user.
4. Requires `users.role === 'collection_agent'` and `AgentDirectoryService.byUserId(user.id)` to find an active HR employee of the Tea Collecting Agent job role linked to a collection-agent dispatch identity. Otherwise it returns 401 ("This account is not a collection agent.").
5. Stamps `last_login_at`.
6. Signs `{ sub: String(user.id), role: 'CollectionAgent' }`.
7. Returns `{ accessToken, agent: { id, name, phone }, mustChangePassword }`. The `agent.id` is `collection_agents.id`, while token `sub` is `users.id`.

The login response deliberately differs from `LoginResult`: it has `agent` and `mustChangePassword`, not `user`. The mobile `auth.api.ts` currently models only `LoginResult`, so it cannot accurately type/consume this endpoint yet.

### Password storage and initial credentials

- `users.password_hash` is a required text column. Runtime login compares a candidate password to it using `bcrypt.compare`; plaintext passwords are not stored.
- Owner self-registration hashes with `bcrypt.hash(..., 10)`.
- `AgentProvisioningService.provision()` generates a temporary password using `randomBytes(9).toString('base64url')`, hashes it at cost 10, creates the user with role `collection_agent`, and sets `must_change_password = true`. The generated value is returned once as `initialPassword` in the employee-create response; the code reviewed does not show a separate email/SMS delivery service.
- The Admin employee create/update flow provisions a login when the selected employee role is `Tea Collecting Agent`. `POST /employees` is the create endpoint, and `EmployeesService.create()` requires an Administrator. It first saves the HR row, calls provisioning, and removes the HR row if provisioning fails. Provisioning writes the user, factory employee subtype, collection-agent dispatch row, and employee-to-user link.
- Important schema/code mismatch to verify: `User.name` is non-null in `user.entity.ts` and `baseline.sql` (`name character varying(32) NOT NULL`), but `AgentProvisioningService.provision()` creates the User with phone, password hash, role, status, and temporary-password flag only; it does not supply `name`. Against that baseline, the user insert can fail at the database NOT NULL constraint. The agent provisioning unit test uses a mock repository and does not prove that this production insert succeeds.
- On the first agent sign-in, `mustChangePassword` is returned to the app. `POST /auth/agent/change-password` compares the current password, rejects reusing the same password, hashes the new one at cost 10, and clears `must_change_password`.
- Every protected agent-self-service operation calls `AgentSelfService.me()`, which checks that the user is not suspended and the temporary-password flag has been cleared. The check is per call, so deprovisioning/suspension and the first-password rule take effect despite an unexpired token.

### JWTs, guards, roles, expiration, and errors

- `AuthModule` requires `JWT_SECRET` and sets `expiresIn` from `JWT_EXPIRES_IN`, defaulting to `7d`. The actual environment values were not inspected or copied into this report.
- `JwtStrategy` extracts the JWT from the Authorization header, verifies signature and expiration (`ignoreExpiration: false`), then accepts only `Administrator`, `Officer`, or `Manager` from `PORTAL_ROLES`.
- `AgentJwtStrategy` uses a separate Passport strategy name (`jwt-agent`) and accepts only the `CollectionAgent` role claim. `AgentJwtGuard` protects the agent API.
- Both token types use the configured JWT secret. Separation is by the validated role claim and distinct guard/strategy, not by a configured JWT `aud` claim.
- `POST /auth/login` and `/auth/mobile/login` share `AuthService.login()`. That service explicitly handles `estate_owner` and `estate_manager`, and its default branch requires `toPortalRole()`. `collection_agent`, `receiving_officer`, and `plucking_employee` are not accepted through this generic branch.
- `toAppRole()` maps factory admin/officer/manager and estate owner/manager. `toPortalRole()` further restricts to the three factory roles. Neither maps Collection Agent or Receiving Officer.
- The API returns distinct 401 messages for unknown phone, wrong password, suspended account, missing profile, and unsupported role. This can reveal account/role state to a caller; consider a uniform public login error if that disclosure is not intended.
- `IdentityThrottlerGuard` is globally registered. The named `auth` throttler is configured for 5 requests per 60 seconds and its path filter covers `/auth/login`, `/auth/mobile/login`, and `/auth/mobile/register`; `/auth/agent/login` does not match that custom filter, although the global short/medium/long throttlers still apply. Verify whether agent login should receive the dedicated auth bucket.
- Portal `JwtStrategy` validates the signed token and role but does not reload the user's status. Thus a portal JWT already issued remains valid until expiry if the account is later suspended; the agent services do reload login status on every agent API call.
- There is no refresh-token endpoint or server-side JWT revocation/blacklist evident in the reviewed authentication code. Logout is therefore client-side token removal.

### Important authorization mismatch: mobile `/me`

`AuthMobileController.me()` uses `JwtAuthGuard`, which selects the `jwt` strategy. That strategy rejects every role outside `PORTAL_ROLES`, including `Estate Owner` and `Estate Manager`. Consequently, an Estate Owner can pass `/auth/mobile/login` and receive a token, but `/auth/mobile/me` will reject that token. The current mobile app does not call `/auth/mobile/me`, so this does not prevent the login screen from reporting success, but it blocks using this endpoint to restore/validate an estate-role session.

### Agent-only endpoints and ownership checks

`DispatchAgentController` is guarded at controller level by `AgentJwtGuard` under `/dispatch/me`. Its endpoints include:

- `POST /dispatch/me/shift/start`, `POST /dispatch/me/shift/end`
- `POST /dispatch/me/absence`, `DELETE /dispatch/me/absence`
- `POST /dispatch/me/pings`
- `GET /dispatch/me/cover-requests`
- `POST /dispatch/me/cover-requests/:id/accept`, `POST /dispatch/me/cover-requests/:id/decline`
- `GET /dispatch/me/stops`
- `POST /dispatch/me/push-token`

Each handler passes the JWT subject (`users.id`) into `AgentSelfService`. The service resolves the active agent using that subject before retrieving or mutating agent-specific data. This prevents a caller from supplying a different agent identity in these request paths. The portal-side `/dispatch/*` controller instead uses `JwtAuthGuard` and the server-driven `dispatch` permission level. Other application controllers also use `JwtAuthGuard`; Collection Agent tokens are rejected by that portal strategy.

## 2. End-to-end Estate Owner login flow

```text
Mobile app auth/login.tsx
  -> app/services/api/auth.api.ts login(phone, password)
  -> POST /auth/mobile/login
  -> AuthMobileController.login(LoginDto)
  -> AuthService.login(phone, password)
  -> UsersService.findByPhone(phone) -> users row
  -> bcrypt.compare(password, password_hash) + users.status check
  -> Estate Owner profile lookup: tea_estate_owners -> estates
  -> JwtService.sign({ sub: users.id, role: 'Estate Owner' })
  -> { accessToken, user }
  -> login screen persists accessToken/user
  -> router.replace('/(estate-owner)/home')
```

Frontend details:

- Screen: `source-code/mobile/src/app/auth/login.tsx`. It validates the phone via `getPhoneNumberError()` and requires a nonempty password. Failed API errors are routed to phone/password field messages where recognized, otherwise to a form-level message.
- Service: `source-code/mobile/src/app/services/api/auth.api.ts`; uses `/auth/mobile/login`.
- API URL: `source-code/mobile/src/app/services/api/client.ts` prefers `EXPO_PUBLIC_API_URL`; fallback uses the Expo dev host and port `3001`. Backend `main.ts` listens on the configured environment port and falls back to `3000`, so the deployment/dev environment must explicitly align these values. The actual runtime URL/port was not inspected.
- Persistence: native runtime writes `accessToken` and serialized `user` to Expo SecureStore keys of those names; web runtime writes them to `localStorage` with the same keys. There is no central session store or boot-time restoration in the reviewed mobile code.
- Navigation: successful Estate Owner login replaces the route with `/(estate-owner)/home`; Estate Manager routes to `/estate-manager`. The code has a redundant second Estate Owner check in the same handler. Other roles show "This account does not have a mobile dashboard yet."
- Logout: the Tea Collector demo profile only shows a confirmation alert; its "Log out" action does not clear stored credentials or navigate away. The estate-owner layout has no logout implementation in the reviewed file.
- Expired/invalid token handling: the mobile API client has no Authorization header and there is no token validation/401 cleanup path. It only parses a JSON response and throws `ApiError` for non-2xx results.
- Registration: `auth/register.tsx` calls `/auth/mobile/register`, but its `persistSession()` helper is not called after the registration result; it navigates to the Estate Owner home without persisting the returned JWT/user.

The Admin web portal has a separate factory-portal login integration, not an Estate Owner UI: `features/auth/LoginPage.tsx` posts phone/password through `services/auth.ts` to `/auth/login`, stores the token via `AuthContext`, and navigates to `/dashboard`. `lib/api.ts` uses `VITE_API_URL` (fallback `http://localhost:3000`), persists the JWT in `localStorage`, sets the Authorization header from the stored JWT on subsequent API requests, and notifies `AuthContext` on 401 so it logs out. `AuthContext` calls `/auth/me` on initial load and provides logout by clearing the token and user state. Its UI says "Sign in to the factory portal"; estate roles are not supported by the portal's protected API strategy.

## 3. Shared user and business-role structure

All implemented login identities use the shared `users` table. `users.role` is the DB role discriminator; the subtype/profile tables associate a login with its business record.

| User type | `users.role` | Profile/identity relationship found in code/schema | Login state found |
|---|---|---|---|
| Estate Owner | `estate_owner` | `tea_estate_owners.user_id` is unique FK to `users.id`; estates refer to `tea_estate_owners.id` through `estates.owner_id`. | Supported by generic/mobile login; no owner-specific token strategy. |
| Estate Manager | `estate_manager` | `users` -> `estate_employees.user_id` -> `tea_estate_managers.employee_id` and the managed estate. | Generic/mobile login maps the role and loads a manager profile. |
| Tea Collector / Collection Agent | `collection_agent` | `users` -> `factory_employees.user_id`; `collection_agents.employee_id` -> `factory_employees.id`; `collection_agents.hr_employee_id` -> `employees.id`; `employees.user_id` -> `users.id`. `AgentDirectoryService` treats an Active employee with job title `Tea Collecting Agent` and a linked login/agent identity as dispatchable. | Dedicated `/auth/agent/login`; temporary password and separate agent guard. |
| Receiving Officer | `receiving_officer` | `users` and `factory_employees` support the role; `receiving_officers.employee_id` links to `factory_employees`. | Role exists in schema but is not mapped by `toAppRole()` or accepted by either current login strategy. |
| Factory Admin | `factory_admin` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Administrator`. |
| Factory Manager | `factory_manager` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Manager`. |
| Factory Officer | `factory_officer` | `users` -> `factory_employees.user_id`; factory employee links to factory. | Supported as portal `Officer`. |
| Plucking Employee | `plucking_employee` | `users` -> `estate_employees.user_id`; plucking profile is separate. | Role exists but is not mapped by the reviewed auth role map. |

The HR `employees` table is separate from `factory_employees`; most employee rows have no login. For Collection Agents, both records are linked to the shared user identity. The `collection_agents` entity has no direct `user_id` property; account resolution goes through the HR/user links above. The existing Admin employee-registration process creates Tea Collector accounts. There is no separate public Collection Agent registration endpoint.

## 5. Mobile authentication and Tea Collector UI

### Existing reusable pieces

- Expo Router stack is configured in `source-code/mobile/src/app/_layout.tsx`.
- Existing phone/password form and field-level errors are in `app/auth/login.tsx`.
- `app/services/api/auth.api.ts` and `app/services/api/client.ts` provide a fetch service and basic API error type.
- SecureStore is already a dependency and the login screen persists access token and user data on native platforms.
- `components/ui/PasswordInput.tsx` and the existing password form can be reused.
- The backend agent endpoint, token strategy, password-change DTO, and dispatch endpoints are ready to be integrated.

### Existing limitations / not implemented

- `source-code/mobile/src/data/userRoles.ts` sends Estate Owner and Estate Manager to `/auth/login`, but sends "Factory Collector" directly to `/teacollector/teacollectorMobile`. That collector destination is a demo screen with hard-coded stops, requests, identity, and interface components; it is not an authenticated data-backed screen.
- The current login API calls `/auth/mobile/login`, whose generic login branch does not accept `collection_agent`. The correct backend login route is `/auth/agent/login`, and its response is `{ accessToken, agent, mustChangePassword }`, not `{ accessToken, user }`.
- `api/client.ts` uses `fetch`, not Axios; despite Axios being a package dependency, no Axios instance/interceptor is used by this authentication service. No Authorization bearer header is added by `apiRequest()`.
- There is no mobile `AuthContext` or Zustand auth store in the reviewed app code. `zustand` is installed but no authentication store use was found.
- No boot-time SecureStore read, `/auth/.../me` hydration, protected-route guard, or centralized 401/expired-token handling was found.
- The existing `auth/change-password.tsx` is a UI stub: its handler only logs fields and contains a TODO; it does not call `/auth/agent/change-password`. It is titled as a normal password change and its link says "Forgot password'" although no forgot-password API was found.
- The demo Tea Collector profile's logout button only presents a confirmation alert and does not clear session data.
- The Estate Owner/Manager token persistence code logs the submitted phone/password object and the returned access token to the JS console in `auth/login.tsx`. Remove such credential/token logging before production use.
- Mobile fallback API port is 3001, while backend default listen port is 3000. Use the actual environment's `EXPO_PUBLIC_API_URL`/`PORT` values to confirm connectivity; those runtime settings were not read.

## 7. Recommended implementation approach (analysis only; not implemented)

### Backend

1. Reuse `AuthService.agentLogin()`, `/auth/agent/login`, `AgentJwtStrategy`, and `AgentJwtGuard`; do not add another password table, JWT strategy, hashing utility, or generic login branch for agents.
2. Reuse the Administrator-only employee registration/update workflow to provision or re-enable accounts. Confirm the one-time `initialPassword` is conveyed to the collector through an approved secure operational channel.
3. Wire the mobile app to the existing agent-specific `/dispatch/me/*` endpoints. Continue deriving agent identity from the JWT subject; do not accept arbitrary agent/user IDs from the client for "my" operations.
4. Review whether agent login should be included in the dedicated auth rate-limit path. The current named auth bucket's path filter excludes `/auth/agent/login`.
5. Separately decide/fix the existing Estate Owner `/auth/mobile/me` guard mismatch before relying on that endpoint for Owner session hydration. Do not solve it by weakening the portal strategy to accept agent or estate roles.
6. Preserve role separation when adding routes: portal controllers use `JwtAuthGuard`; agent-self routes use `AgentJwtGuard`; service-level permission and subject ownership checks remain server-side.

Current Mobile Authentication Findings

1. Existing login screen and UI components

- Screen: `source-code/mobile/src/app/auth/login.tsx` (`LogInScreen`). This is the existing phone-and-password screen used by Estate Owners and Estate Managers.
- It composes shared UI components from `source-code/mobile/src/components/ui/`: `Screen`, `AppText`, `AppInput`, `PasswordInput`, and `AppButton`.
- It also uses React Native `View`, `Image`, and `Pressable`; the brand image is `source-code/mobile/src/assets/brand/logo&wordmark/png/FullLogoGreen.png`.
- `AppInput` collects the phone number and `PasswordInput` collects the password. The screen performs phone/password validation, displays field/form errors and loading state, and submits with the Sign in button. It includes links to `/auth/change-password` and `/auth/register`.
- Although often described as the Estate Owner login, the same screen also serves the Estate Manager; it branches on the returned user role after successful login.

2. Authentication API function

- The screen imports and calls `login(phoneNumber, password)` from `source-code/mobile/src/app/services/api/auth.api.ts`.
- That function sends `POST /auth/mobile/login` with `{ phone, password }` through `apiRequest` in `source-code/mobile/src/app/services/api/client.ts`.
- The mobile endpoint is implemented by `source-code/backend/src/auth/auth.mobile.controller.ts` and calls the generic `AuthService.login()`. Its response is `{ accessToken, user }`.
- The screen persists the token and user in SecureStore on native platforms (or localStorage on web). It routes Estate Owners to `/(estate-owner)/home` and Estate Managers to `/estate-manager`.

3. Navigation to the login screen

- `source-code/mobile/src/app/_layout.tsx` registers `auth/login` as an Expo Router stack screen. The route is also available directly as `/auth/login`.
- The app's root `source-code/mobile/src/app/index.tsx` replaces the initial route with `/(onboarding)` after its splash delay.
- From `source-code/mobile/src/app/(onboarding)/index.tsx`, Get Started navigates to `/(onboarding)/select-role`.
- `source-code/mobile/src/data/userRoles.ts` sets both Estate Owner and Estate Manager routes to `/auth/login`, so selecting either role opens this screen.
- Factory Collector currently routes to `/teacollector/teacollectorMobile`, not to the login screen. That destination is a demo experience, not a login flow.

4. Reuse for Tea Collector login

The visual/form portion is reusable, but this screen cannot authenticate and enter the Tea Collector app unchanged.

- The existing screen calls `/auth/mobile/login`; Tea Collectors have a separate backend endpoint, `POST /auth/agent/login`, implemented in `source-code/backend/src/auth/auth.controller.ts` and `AuthService.agentLogin()`.
- The agent endpoint returns `{ accessToken, agent, mustChangePassword }`, rather than the current `{ accessToken, user }` shape. It also issues an agent-specific token, and the backend has a separate agent change-password endpoint at `/auth/agent/change-password`.
- The current success handler only routes Estate Owner and Estate Manager roles. It does not handle the agent response or navigate to the Tea Collector experience.
